## แก้ไขปัญหา Browser Cache รูปโลโก้หน้าล็อกอินผู้ดูแลระบบ (admin/login.php)

* **ผลการพัฒนา / การแก้ไข (สำหรับนำไปใส่บทที่ 4):**
  - เพิ่ม Dynamic Cache Buster ให้กับแท็ก <img> ของโลโก้ในไฟล์ admin/login.php โดยใช้ฟังก์ชัน filemtime()
  - ทำให้ทุกครั้งที่มีการเปลี่ยนไฟล์ภาพ ts-pattani-generated.jpg เบราว์เซอร์จะดึงภาพใหม่มาแสดงผลทันทีโดยไม่ต้องสั่ง Hard Refresh
* **ปัญหาที่พบและวิธีแก้ (สำหรับนำไปใส่บทที่ 5):**
  - ปัญหา: เมื่อผู้ใช้เปลี่ยนไฟล์ภาพในโฟลเดอร์ assets/img/ แต่หน้าเว็บยังคงแสดงผลเป็นภาพเดิมเนื่องจากเบราว์เซอร์จำค่าแคช (Browser Caching)
  - วิธีแก้: ต่อท้าย URL รูปภาพด้วยพารามิเตอร์ ?v=filemtime(...) เพื่อทำ Cache Busting อัตโนมัติตามเวลาที่มีการแก้ไขไฟล์ล่าสุด

## ปรับปรุงโครงสร้างการแสดงผลการ์ดคอร์ทสนาม (Court Card UI) ในตาราง Matrix Grid

* **ผลการพัฒนา / การแก้ไข (สำหรับนำไปใส่บทที่ 4):**
  - ปรับปรุงการจัดวางองค์ประกอบภายในกล่องการ์ดคอร์ทสนาม (.court-card-v2) ในหน้าจองสนาม (booking.php) ตามหลักการออกแบบ HCI และคำขอของผู้ใช้
  - แยกข้อมูลเป็น 3 ส่วนในแนวตั้งอย่างสมดุล:
    1. ด้านบน: ไอคอนและชื่อคอร์ทสนาม (.court-card-title)
    2. ตรงกลาง: ชื่อเล่นของผู้จองสนาม (.court-card-user) หรืออัตราค่าบริการรายชั่วโมง พร้อมระบบตัดคำอัตโนมัติ (Text Ellipsis) ป้องกันข้อความล้น
    3. ด้านล่าง: ป้ายสถานะ (.court-card-badge) แสดงเฉพาะสถานะสั้นกระชับ (● ว่าง, ✓ กำลังเลือก, ● รอตรวจสอบ, ● จองแล้ว, ● ปิดปรับปรุง, ● ปิดบริการ)
  - เพิ่มการรองรับการแสดงผลบนหน้าจอมือถือ (Responsive <= 576px) โดยจัดเป็น 2 คอลัมน์อย่างสวยงาม สมดุล และสัมผัสใช้งานได้ง่าย
* **ปัญหาที่พบและวิธีแก้ (สำหรับนำไปใส่บทที่ 5):**
  - ปัญหา: โครงสร้างเดิมนำชื่อผู้จองไปใส่รวมในป้ายสถานะ (Badge) เดียวกัน เช่น "● จองแล้ว (สมชาย)" ทำให้ป้ายยาวเกินขนาดการ์ด ตัวอักษรตกขอบ และทำให้อ่านชื่อผู้จองไม่ชัดเจน
  - วิธีแก้: แยกคอนเทนเนอร์ชื่อผู้จองออกมาไว้ตรงกลางกล่อง (.court-card-user) พร้อมไอคอนกำกับสถานะ (User icon / Clock icon) และปรับปรุงให้ Badge สถานะคงความกะทัดรัด สะอาดตา ถูกต้องตามหลัก Visual Hierarchy

## ปรับลดการแสดงผลราคาในกล่องคอร์ทสนาม (Remove Price from Court Cards)

* **ผลการพัฒนา / การแก้ไข (สำหรับนำไปใส่บทที่ 4):**
  - นำตัวเลขราคา (เช่น 150 ฿/ชม.) ออกจากการ์ดคอร์ทสนาม (.court-card-v2) ตามคำขอของผู้ใช้ เพื่อลดความซ้ำซ้อนของข้อมูล (Information Redundancy) เนื่องจากระบบมีแถบแสดงอัตราค่าบริการของวันและช่วงเวลานั้นๆ (Date Price Banner) ที่ด้านบนของตาราง และมีแถบสรุปราคารวม (Sticky Summary Bar) ด้านล่างอยู่แล้ว
  - ปรับการแสดงผลส่วนกลางให้แสดงเฉพาะกรณีที่มีผู้จองสนามแล้วเท่านั้น (ชื่อเล่นผู้จองพร้อมไอคอน 👤 หรือ 🕒) ส่วนกรณีคอร์ทว่างจะแสดงเฉพาะไอคอน ชื่อคอร์ท และป้ายสถานะ ● ว่าง ที่กึ่งกลางกล่องอย่างสะอาดตา
  - กำหนด min-height: 108px และ justify-content: center เพื่อให้ขนาดความสูงและการจัดกึ่งกลางของการ์ดทุกใบในแถวตารางมีความสม่ำเสมอเท่ากันทั้งหมด
* **ปัญหาที่พบและวิธีแก้ (สำหรับนำไปใส่บทที่ 5):**
  - ปัญหา: การแสดงตัวเลขราคาในทุกการ์ดทำให้หน้าจอแลดูรก มีข้อมูลซ้ำซ้อน และดึงความสนใจไปจากสถานะความว่างของสนาม
  - วิธีแก้: ซ่อนราคาในระดับการ์ดรายชั่วโมง และเน้นเฉพาะชื่อคอร์ทกับชื่อผู้จอง ช่วยเพิ่มพื้นที่ว่าง (White Space) และความสบายตาในการมองหาคอร์ทที่ต้องการ

## สรุปคู่มือทำความเข้าใจสถาปัตยกรรมระบบและเตรียมสอบโปรเจกต์ (Technical Defense Preparation Guide)

* **ผลการพัฒนา / การแก้ไข (สำหรับนำไปใส่บทที่ 4):**
  - สแกนและถอดรหัสโครงสร้างสถาปัตยกรรมระบบ T.S. Pattani ทั้งหมดแบบองค์รวม โดยไม่มีการแก้ไขโค้ดหรือฐานข้อมูล
  - จัดทำตารางแมปปิ้งความเชื่อมโยงระดับไฟล์แบบครบวงจร: หน้า View <---> ไฟล์ JavaScript ควบคุม <---> ไฟล์ Action Controller ปลายทาง <---> ตารางฐานข้อมูลที่ได้รับผลกระทบ

  - จัดทำคลังคำตอบดักคำถามกรรมการ (Top 10 Technical Q&A) สำหรับใช้ตอบปากเปล่าในห้องสอบ

  - วิธีแก้: สรุปตรรกะเชิงลึกเป็นภาษาที่เข้าใจง่าย กระชับ พร้อมชี้ให้เห็นเจตนารมณ์ของการออกแบบ (Design Rationale) เพื่อใช้เป็นอาวุธในการนำเสนอหน้าห้องสอบ

## จัดทำคู่มือทำความเข้าใจระบบและเตรียมสอบโปรเจกต์ฉบับแผนภาพและไดอะแกรม (Visual Defense Handbook Artifact)

* **ผลการพัฒนา / การแก้ไข (สำหรับนำไปใส่บทที่ 4):**
  - สร้างเอกสาร Markdown พร้อมแผนภาพประกอบ (Mermaid Diagrams) สำหรับใช้เตรียมตัวสอบโครงงานฉบับสมบูรณ์ที่ [ts_pattani_defense_guide_and_diagrams.md](file:///C:/Users/Lenovo/.gemini/antigravity/brain/7271809d-d8a7-4f35-89ee-a775107f6980/ts_pattani_defense_guide_and_diagrams.md)
  - ประกอบด้วยแผนภาพ 5 รูปแบบหลัก:
    - *แผนภาพสถาปัตยกรรมระบบภาพรวม (System Architecture Overview):* แสดงความสัมพันธ์ 4 เลเยอร์ (Client, Security, Controller, Database)
    - *Sequence Diagram วงจรการจองสนาม (Booking Flow):* แสดงการทำงานตั้งแต่เลือกเวลา -> คำนวณราคา -> ล็อกแถวด้วย `SELECT ... FOR UPDATE` -> ล็อกคิว 15 นาที
    - *Sequence Diagram วงจรการชำระเงินและตรวจสลิป (Payment & Verification Flow):* แสดงการแนบสลิป -> แอดมินตรวจ -> อนุมัติ -> บันทึก Revenue -> แจกแต้ม Point
    - *Sequence Diagram วงจรระบบหลังบ้าน (POS & Operations Flow):* แสดงการคิดเงินหน้าร้าน, การตรวจรับคืนอุปกรณ์/คิดค่าปรับ, และการส่งซ่อมสนาม
    - *Flowchart ตรรกะการคิดราคา (Pricing Logic Flowchart):* แสดงการแยกคิดราคาตามวันเสาร์-อาทิตย์, วันธรรมดากลางวัน, วันธรรมดาช่วงค่ำ, และการคำนวณคาบเกี่ยวช่วงเวลา (Cross-Window)
  - รวบรวมตารางแมปปิ้งระดับไฟล์ และตาราง Cheat Sheet คลังคำตอบดักคำถามกรรมการ 10 ข้อ ไว้อย่างเป็นระเบียบ
* **ปัญหาที่พบและวิธีแก้ (สำหรับนำไปใส่บทที่ 5):**
  - ปัญหา: ข้อความอธิบายแบบ Text ล้วนอาจทำให้ผู้จัดทำจินตนาการเส้นทางการไหลของข้อมูล (Data Flow) และลำดับการประมวลผลของระบบได้ยาก
  - วิธีแก้: แปลงข้อความให้อยู่ในรูปแผนภาพไดอะแกรม Mermaid ที่เห็นการโต้ตอบระหว่าง Entity (Actor, View, Script, Controller, Database) ทำให้ผู้จัดทำเข้าใจโครงสร้างลึกซึ้งและนำไปใช้อธิบายหรือฉายสไลด์ในห้องสอบได้ทันที

## สรุปยุทธวิธีรับมือและตอบคำถามสดหน้าห้องสอบโปรเจกต์ (Live Defense Survival Tactics)

* **ผลการพัฒนา / การแก้ไข (สำหรับนำไปใส่บทที่ 4):**
  - จัดทำกรอบแนวคิดและสคริปต์การตอบคำถาม 3 สถานการณ์จำลองยอดฮิตที่กรรมการสอบมักใช้ทดสอบความรู้เชิงลึกของนักศึกษา:
    1. *กรณีให้อธิบายโค้ด (Code Explanation):* กำหนดสูตร 4 สเต็ป (Input/Output ภาพรวม -> เจาะการทำงานทีละบรรทัด -> ชี้จุดเด่นความปลอดภัยและ Best Practice -> สรุปผลลัพธ์) พร้อมตัวอย่างโค้ดจริงใน `booking_db.php`, `functions.php`, และ `pos_checkout_db.php`
    2. *กรณีให้เพิ่มตารางฐานข้อมูล (Schema Extension):* กำหนดโฟลว์ตอบอย่างเป็นระบบ (ถาม Requirement -> กำหนด PK/FK และ Data Types ตามหลัก Normalization -> วิเคราะห์ผลกระทบระดับโค้ด Model/Action/View) พร้อมเคสศึกษาการเพิ่มตาราง `Coach_Booking`
    3. *กรณีให้เปลี่ยนค่าตัวแปรหรือแก้โค้ดสด (Live Code Modification):* กำหนดวิธีวิเคราะห์ Blast Radius (พูดผลกระทบที่คาดว่าจะเกิดขึ้นก่อนแก้ -> เช็ค Scope และ Type ด้วย Search -> บันทึกและรีเฟรชหน้าจอโชว์ผลลัพธ์)
  - กำหนดชุดประโยคทองคำเชิงจิตวิทยาและการสื่อสารเพื่อรักษาความมั่นใจหน้าห้องสอบ
* **ปัญหาที่พบและวิธีแก้ (สำหรับนำไปใส่บทที่ 5):**
  - ปัญหา: นักศึกษามักเกิดความตื่นตระหนกและประหม่าเมื่อกรรมการสั่งให้เปิดดูโค้ด สั่งให้แก้ตัวแปร หรือตั้งโจทย์สมมุติเกี่ยวกับฐานข้อมูล ทำให้ตอบไม่ตรงประเด็นหรือเกิดอาการพูดไม่ออก
  - วิธีแก้: วางโครงสร้างการตอบเป็นสูตรสำเร็จ (Mental Framework) ให้ผู้จัดทำสามารถดึงมาใช้เป็นแกนหลักในการตอบได้ทุกสถานการณ์ แสดงให้เห็นถึงวุฒิภาวะทางวิศวกรรมซอฟต์แวร์และการคิดอย่างเป็นระบบ
